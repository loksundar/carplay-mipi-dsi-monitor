# Turn the CarPlay screen into a Mac sidekick

**Bottom line.** The best plan is to keep the V831 a thin client: the Mac does the heavy work and the screen shows pixels and sends back touches. One small C program on the device that draws compressed tiles into fb0 and reports GT911 touches over the network can serve the Mac extended display, Mac-rendered web pages and dashboards, and a macro pad. Building that one program unlocks about two-thirds of what you want. Music is the easiest standalone win. **shairport-sync-mini (AirPlay 1)** and **mpg123** both exist as tiny prebuilt musl packages for this exact CPU, and the QN8027 FM transmitter you confirmed at i2c-3/0x2c gives in-car output. YouTube video on the device is the hard part. The SoC does have a hardware H.264 decoder that the stock CarPlay app uses, but its libraries are statically linked into `sdvcam`, so getting to it is a research project. YouTube *audio*, resolved on the Mac with yt-dlp, is easy now. A browser running on the device itself (Chromium, WPE) does not fit in 91.5 MB. The one on-device option that does, FBrowser/QtWebKit loaded from a RAM squashfs, peaks around 75–80 MB and only handles simple pages. Nobody has published work turning these V831 CarPlay screens into a display, media player or touch device, so you would be first. Several building blocks already exist, though: OpenDisplay's Mac sender, fbvnc, LVGL, the Companion Satellite protocol, and OpenWrt's armv7 packages.

## Five projects, ranked by value for effort

The ranking weighs what you get against how much work and risk it takes. It also prefers your constraints: nothing written to flash beyond the ~8.7 MB rootfs headroom, no kernel rebuild, and nothing that could break WiFi, since a dead network means opening the case.

| Rank | Project | Goal served | Feasibility on this hardware | Effort (hobbyist) | Main risk |
|---|---|---|---|---|---|
| 1 | **AirPlay 1 + radio player with FM/AUX output** (shairport-sync-mini, mpg123) | Music | High: tiny musl packages for this exact ABI | 1–3 evenings | Finding the ALSA mixer settings and the QN8027 init sequence |
| 2 | **"Tile client" + Mac virtual display** (CGVirtualDisplay + ScreenCaptureKit → JPEG/raw dirty tiles → fb0, touch → CGEvent) | Mini display, touch | High at ~10–15 fps full-screen, smoother for normal desktop use (estimate) | 1–3 weekends | Private macOS API can break on OS updates; fb0 pan cost on full-frame motion |
| 3 | **Mac-rendered web/HA dashboard** (headless Chrome CDP screencast over the same tile client, touches as CDP input) | Web | High; reuses project 2's device code | 1 weekend after #2 | ~100 ms+ touch latency; Mac must be on |
| 4 | **Touch macro pad** (native C Companion Satellite client, or LVGL buttons) | Touch | High: LVGL needs <1 MB; Satellite is a line-based text protocol | 1–2 weekends | No existing armv7 client, so you write it |
| 5 | **YouTube video**: yt-dlp on the Mac; device plays via (a) Mac display stream, (b) software ffmpeg at 360p, or (c) hardware VE decode | YouTube | (a) works but choppy; (b) borderline; (c) proven in silicon but blocked on missing SDK libs | (a) free after #2; (b) days; (c) weeks, uncertain | No public V831 decode sample; YouTube changes break yt-dlp often |

Music comes first because you can finish it in a weekend and it uses hardware you have just verified (ES8388 on ALSA card 2, QN8027 on i2c-3). The tile client comes second because it is the shared foundation: projects 3, 4 and option 5a sit on the same device binary. Your existing `fbdash` already does a slow version of this, pulling one raw 3.84 MB frame every 30 seconds. Upgrading it to push-based compressed dirty tiles plus a touch uplink is an extension of working code, not new territory.

## A Mac extended display works if the Mac does almost everything

### macOS can create the extra screen, but only through a private API

There is **no public macOS API for creating a virtual display**. Every tool that does it without a dongle, including BetterDisplay, uses the undocumented `CGVirtualDisplay` classes. The only public alternative is a DriverKit extension that needs an Apple-granted entitlement ([go-macos/virtualdisplay](https://pkg.go.dev/github.com/go-macos/virtualdisplay)). That library is BSD-licensed and was tested on **macOS 26.6.2 on an M4 Max**. It accepts any size from 64 to 16384 px, so 1600x600 is fine. The display exists only while the creating process runs, which is useful: quit the daemon and the screen disappears cleanly. Two traps are documented. Changing the display's mode makes it impossible to remove until the process exits, and the library leaves an ICC profile behind in `/Library/ColorSync/Profiles/Displays`. One developer's 2026 notes say macOS sometimes moves a virtual display to a different position after a reconfiguration ([jorvik-software notes](https://jorvik-software.pages.dev/notes/2026/04/11/when-the-stars-align-redux)). Recompute touch mapping whenever the display layout changes.

BetterDisplay is a no-code alternative for creating the screen, but **it has no network streaming**. Its "streaming" only moves content between screens attached to the same Mac, and custom virtual-screen configurations (a 1600x600, 8:3 screen probably counts) are a Pro feature ([BetterDisplay Free vs Pro](https://github.com/waydabber/BetterDisplay/wiki/List-of-free-and-Pro-features)). You would still have to write the capture-and-send part yourself, so a small custom daemon is the cleaner choice. FluffyDisplay, an older free option, is archived and broke on Sonoma ([issue #19](https://github.com/tml1024/FluffyDisplay/issues/19)).

### OpenDisplay has already built most of the Mac side

**OpenDisplay** ([peetzweg/opendisplay](https://github.com/peetzweg/opendisplay)) is the closest existing work. It creates a CGVirtualDisplay sized to the receiver, captures it with ScreenCaptureKit, encodes real-time H.264/HEVC with VideoToolbox, and sends it over a single TCP connection (USB or WiFi) using 4-byte length-prefixed frames. Touches come back as JSON and are injected as CGEvent click, drag and scroll, which needs the Accessibility permission. Its receivers are Apple devices, so you would keep the Mac sender and write your own V831 receiver. Current versions are **GPL-3.0; releases up to v0.4.x are MIT**, so fork an old tag if the licence matters to you. Its `CGVirtualDisplayPrivate.h` is a clean reference header for the private API.

Capture should use ScreenCaptureKit. Set `minimumFrameInterval` to cap the frame rate, and read the per-frame **`dirtyRects`** attachment so only changed regions are encoded and sent. Apple's WWDC22 session demonstrates exactly this pattern ([WWDC22 10155](https://developer.apple.com/la/videos/play/wwdc2022/10155/); [dirtyRects docs](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo/dirtyrects.md)). The cursor is not always included in macOS captures. The ESP32 "flea cinema" second-screen project draws it manually for that reason ([Hackster](https://www.hackster.io/news/use-an-esp32-as-an-itty-bitty-second-monitor-for-your-pc-647b269b1d1b)).

### The device is the bottleneck, so send JPEG dirty tiles rather than H.264

A raw 1600x600 BGRA frame is 3.84 MB. At 15 fps that is about 460 Mbit/s, which neither WiFi nor USB 2.0 can carry. Compression is mandatory. The question is which compression a single 1 GHz Cortex-A7 can decode. The best published reference point is a Raspberry Pi 2 (Cortex-A7) decoding 640x480 JPEGs with NEON libjpeg-turbo at **85 images/s single-threaded, about 26 MP/s** ([info-beamer](https://info-beamer.com/blog/omx-jpeg-decoding-performance-vs-libjpeg-turbo)). Scaled to the V831's weaker memory, a full 0.96 MP frame takes an estimated **35–50 ms**, so roughly **10–15 fps for full-screen motion at 100% CPU**. This estimate is unverified; run `tjbench` on the device before committing. Normal desktop use changes well under a tenth of the screen per frame, so dirty-tile updates should feel smooth. VNC Tight encoding works on weak clients for the same reason.

There is one device-specific wrinkle. **fb0 only reaches the panel when you call `FBIOPAN_DISPLAY` with the dirty rectangle in `var.reserved[0..3]`.** Each pan makes the kernel rotate that rectangle in software (NEON, writing into uncached memory; see `<project>/ref/disp_rotation_sw.c`). Small rectangles are cheap and full frames are expensive. Your tile client should decode tiles straight into the fb0 mapping (TurboJPEG `tjDecompress2` with `TJPF_BGRA`) and issue one pan per frame covering the union of the changed tiles. If full-motion content later turns out to need more speed, the stock firmware shows the faster route. It allocates ION buffers, rotates with the G2D engine, and flips a separate display-engine layer through `DISP_LAYER_SET_CONFIG2` on `/dev/disp`. That route bypasses fb0's software rotation and needs no kernel change ([Radxa G2D guide](https://docs.radxa.com/en/cubie/a5e/app-dev/npu-dev/g2d-usage-guide); [G2D example code](https://github.com/Ronin-1124/allwinner-g2d-usage-guide)). Treat it as a later upgrade: the 4.9 sun8iw19 G2D header was not found online, so you would need to test it on the device.

If you would rather not design a protocol, VNC is the off-the-shelf fallback. **fbvnc** is a tiny framebuffer VNC client that Alpine packages for armv7 musl, and forks of it add touch input and ZLIB ([aligrudi/fbvnc](https://github.com/aligrudi/fbvnc); [uklatt fork](https://github.com/uklatt/fbvnc); [Alpine armv7](https://pkgs.alpinelinux.org/package/edge/community/armv7/fbvnc)). It would need a patch to call the dirty-rect pan. It also lacks Tight-JPEG, and macOS's built-in Screen Sharing serves every monitor rather than one chosen display ([Apple Discussions](https://discussions.apple.com/thread/8199989?page=1)), so you would still need a custom RFB server on the Mac. A custom tile protocol ends up being less total work.

### Transport: WiFi first, USB NCM as an upgrade

Use WiFi first, because it already works. The BCM4334 is a 1x1 802.11n chip. Realistic TCP throughput is an unmeasured estimate of 20–40 Mbit/s, which is plenty for JPEG tiles. **USB NCM** is available as a gadget function. On USB 3 hardware it outperforms ECM by about 3x ([Purism MR 342](https://source.puri.sm/Librem5/librem5-base/-/merge_requests/342)), but on a USB 2.0 i.MX6 it used about 21.5% CPU at 100 Mbit/s ([NXP forum](https://community.nxp.com/t5/i-MX-Processors/g-ncm-driver-blocks-CPU-for-small-USB-packets/m-p/521672)), so on one A7 core it costs CPU you also need for decoding. Two more caveats. `otg_role` is currently `usb_host`, and switching it to peripheral is untested. Also check whether that USB port is part of your FEL recovery path before experimenting. Neither UVC nor HID gadget functions are available, so the screen cannot appear to the Mac as a plain USB monitor. FunctionFS could expose a custom vendor interface, but the Mac would still need a userspace client, so it gains nothing over NCM plus TCP.

| Mini-display approach | Verdict | Why |
|---|---|---|
| Custom Mac daemon (CGVirtualDisplay + SCK) → JPEG/raw dirty tiles → C tile client on fb0 | **Do this** | Everything runs in user space, nothing touches flash (binary under 1 MB), and it reuses fbdash code |
| Fork OpenDisplay sender (MIT ≤v0.4.x), swap H.264 for JPEG tiles | **Do this (shortcut)** | Saves the virtual-display, capture and touch-injection work |
| fbvnc + custom RFB server on the Mac | Fallback | Needs patching on both ends; no JPEG encoding |
| OpenDisplay unchanged (H.264) + hardware VE decode on device | Later, if the SDK appears | Best quality, blocked by statically linked MPP |
| Deskreen / Weylus / Spacedesk / Sidecar / Duet | No | Need a browser or a proprietary client; Spacedesk has no Mac server |
| USB UVC/DisplayLink-style gadget | No | No UVC function in this kernel; macOS has no driver for a custom class |

## Web and YouTube belong on the Mac, with one narrow on-device exception

### No modern browser fits in 91.5 MB, and only QtWebKit comes close

Chromium is not an option. Its own startup check warns below **1 GB of RAM** ([FullPageOS PR #672](https://github.com/guysoft/FullPageOS/pull/672)), and Pi Zero users report crashes at 512 MB ([MagicMirror forum](https://forum.magicmirror.builders/topic/18200.rss)). CEF and Electron are Chromium plus more. WPE WebKit has a CPU-only Skia mode ([WPE env vars](https://people.igalia.com/aperez/Documentation/wpe-webkit/environment-variables.html)), but its backends assume EGL. A 2019 attempt to run it on fbdev failed at EGL initialisation ([webkit-wpe list](https://lists.webkit.org/pipermail/webkit-wpe/2019-July/000202.html)), and the only footprint figure available is about 100 MB of RAM from around 2017 ([GENIVI deck](https://wiki.covesa.global/download/attachments/364316/GENIVI-open-source-browser-space.pdf?api=v2)). **NetSurf's framebuffer port** draws directly to fbdev and has been used for embedded kiosks, but its JavaScript is incomplete and off by default ([NetSurf](https://en.wikipedia.org/wiki/NetSurf)). It suits only static HTML you write yourself.

The earlier FBrowser study in this project still holds, with the coordinator's facts applied. QtWebKit 5.212 plus ICU and Qt comes to about **20–25 MB as an xz squashfs**. That is far more than the 8.7 MB of free flash, and NFS/CIFS/FUSE are not in the kernel, so the image has to be downloaded into the ~61 MB `/tmp` and loop-mounted. It must be built with the **patched vendor mksquashfs**, because the kernel expects a reordered superblock. Estimated peak use is **75–80 MB of 91.5 MB**: about 22 MB for the image held in RAM, 15–20 MB of page cache, and 30–40 MB for the browser. That leaves 10–20 MB of headroom, enough for a simple page and not enough for any modern JavaScript framework. Qt's linuxfb plugin also never pans, so it needs either a patch or a helper that pans the whole screen about 4 times a second. Turn off FBrowser's `OSBridge`, which lets page JavaScript run root commands. A working SD card would save the 22 MB image cost. These are estimates; measure MemAvailable for ten minutes with a test page before relying on it.

### Rendering on the Mac gives you the full modern web

The proven alternative is to run headless Chrome on the Mac and stream what it draws. Chrome's DevTools `Page.startScreencast` pushes JPEG frames only when the page repaints, with about **100 ms per-frame latency** compared with 250–500 ms for polled screenshots ([sentinel-stack v3.4.0](https://github.com/azfarh95/sentinel-stack-public/releases/tag/v3.4.0)). One tuned setup measured about 15 fps at the source and 7 fps net ([sentri screencast.js](https://rameshbabuprudhvi.github.io/sentri/docs/jsdoc/runner_screencast.js.html)). Each frame must be acknowledged or the stream stalls. Touches go back as `Input.dispatchTouchEvent` or `dispatchMouseEvent` calls. This uses project 2's device binary unchanged, and full Lovelace, Grafana or any site renders correctly. If polling every few seconds is enough, Kindle and TRMNL dashboard projects already produce server-rendered PNGs of Home Assistant views ([hass-lovelace-kindle-screensaver](https://community.home-assistant.io/t/home-assistant-dashboard-on-kindle/186110); [TRMNL byos_hanami](https://github.com/usetrmnl/byos_hanami)). Your current fbdash loop is already that pattern. The proposal is effectively that kind of display with interactivity added. No existing project combines CDP screencast, Linux fbdev and touch forwarding, so the glue is yours to write.

### YouTube: separate the video URL from the decoder

**yt-dlp has to run on the Mac.** Since version 2025.11.12 it needs an external JavaScript runtime (Deno by default) for full YouTube support, and without one "available formats may be limited" ([yt-dlp #15012](https://github.com/yt-dlp/yt-dlp/issues/15012)). The OpenWrt yt-dlp and python3-light packages alone are 5.1 MB and 2.8 MB compressed ([OpenWrt 24.10 index](https://downloads.openwrt.org/releases/24.10.0/packages/arm_cortex-a7_neon-vfpv4/packages/)), before adding Deno. A Go extractor, ytgo, claims to return direct stream URLs without running JavaScript ([tituscheng/ytgo](https://github.com/tituscheng/ytgo)), but it is about 11 MB and unproven against YouTube's frequent changes.

Decoding is the real problem. A Cortex-A8 runs at 100% CPU on 480p H.264 ([TI E2E](https://e2e.ti.com/support/processors-group/processors/f/processors-forum/273437/am335x-maximum-h-264-decode-capability)). Software decode on this chip therefore realistically means **360p H.264 (YouTube itag 18)**, scaled up, with nothing to spare. This is an estimate: benchmark with `ffmpeg -threads 1 -benchmark`. The SoC itself can decode better. Strings extracted from the stock `sdvcam` binary show the complete eyesee-mpp `AW_MPI_VDEC_*` → `AW_MPI_VO_*` pipeline, cedarc's H.264 and H.265 decoders, `/dev/cedar_dev` and `/dev/ion` opens, and G2D rotation. **The V831's video engine does hardware decode, even though Sipeed's spec page lists only an encoder** ([Sipeed M2](https://wiki.sipeed.com/hardware/en/maixII/M2/introduce.html); local evidence: strings of the `sdvcam` in the firmware backup). The catch is that the libraries are **linked statically into `sdvcam`**, and Sipeed declined to provide V831 decode examples ([libmaix #19](https://github.com/sipeed/libmaix/issues/19)). You would need the Tina V83x SDK's eyesee-mpp static libraries and headers, or a way to feed H.264 to `sdvcam` through its CarPlay input path. When encoding for Allwinner decoders, use Baseline profile with no B-frames, as MaixPy recommends ([MaixPy video](https://wiki.sipeed.com/maixpy/doc/zh/video/play.html)).

|---|---|---|
| Mac headless Chrome → CDP JPEG screencast → tile client; touches → CDP input | **Recommended for web** | Full modern web, near-zero device RAM risk, ~100 ms+ latency |
| Polled PNG dashboard (Kindle/TRMNL style) via existing fbdash | **Already working (cheapest)** | Add touch hotspots that POST to the Mac |
| FBrowser/QtWebKit 5.212 from a RAM squashfs | Possible, tight | ~75–80 MB peak (estimate); simple pages only; unmaintained engine with CVEs |
| NetSurf-fb | Possible, limited | Static HTML/CSS only; needs a pan patch |
| WPE / Chromium / CEF / Electron | **No** | EGL dependency and/or ≥ several hundred MB of RAM |
| YouTube: play in Chrome on the Mac's virtual display, view via project 2 | Works, choppy | ~10–15 fps full-motion (estimate), audio stays on the Mac or goes via AirPlay |
| YouTube: Mac yt-dlp → URL → device ffmpeg software 360p | Borderline | Needs an ffmpeg build in tmpfs; benchmark first |
| YouTube: hardware VE decode via eyesee-mpp | High value, blocked | Proven in silicon; needs the vendor SDK or reuse of `sdvcam` |
| yt-dlp on the device | **No** | Python + JS runtime exceed flash and strain RAM |

## Music is the quickest win, using parts you already verified

OpenWrt 24.10 publishes prebuilt **musl packages for exactly this ABI (`arm_cortex-a7_neon-vfpv4`)**: shairport-sync-mini (169.6 KB), mpg123 (89.1 KB), mpd-mini (370.1 KB), alsa-lib (365.1 KB), alsa-utils (134.9 KB), upmpdcli and nqptp ([OpenWrt 24.10 index](https://downloads.openwrt.org/releases/24.10.0/packages/arm_cortex-a7_neon-vfpv4/packages/)). These packages link against OpenWrt's own musl and libraries. Unpack them into a self-contained prefix on the Mac, including OpenWrt's `ld-musl-armhf.so.1`, and run them through that loader or a chroot. Do not mix them with Tina's libc. The music research note suggested hosting this over NFS or an SD card. **NFS is not in this kernel and the SD slot does not currently initialise**, so the prefix goes either into the ~8.7 MB of free flash, where the AirPlay 1 set (about 1.5 MB) fits, or into tmpfs/squashfs downloaded at boot, which is the RAM-only option with zero flash risk.

**AirPlay 1 is the top pick.** The mini variant is built with mbedTLS and the built-in tinysvcmdns, so it needs neither Avahi nor D-Bus. Its installed size is about 97 kB ([OpenWrt shairport-sync-mini](https://openwrt.org/packages/pkgdata/shairport-sync-mini)), and the mbedTLS build supports classic AirPlay only ([OpenWrt Makefile](https://git.cdn.openwrt.org/feed/packages/tree/sound/shairport-sync/Makefile)). Macs and iPhones can still send to AirPlay 1 targets, so the iPhone YouTube Music app or Mac Music can play to the screen directly. AirPlay 2 is a stretch. Upstream says Pi Zero-class single-core hardware is "not really suitable for AirPlay 2 operation" and recommends a Pi 2 or Zero 2 W ([shairport-sync GetTheBest](https://www.github.com/mikebrady/shairport-sync/blob/master/ADVANCED%20TOPICS/GetTheBest.md)). It also needs nqptp with exclusive use of UDP 319/320 and an FFmpeg AAC decoder ([AIRPLAY2.md](https://github.com/mikebrady/shairport-sync/blob/master/AIRPLAY2.md)).

Other good options are **mpg123** for internet radio and for Mac-transcoded YouTube audio (the Mac runs `yt-dlp | ffmpeg` to MP3 over HTTP and the device plays the URL), **librespot** for Spotify Connect, and **snapclient** for multi-room playback. Recent librespot releases (v0.7 through v0.8) moved to Spotify's newer login and connection protocols. It needs **Premium** and will need updating whenever Spotify changes its servers ([librespot releases](https://github.com/librespot-org/librespot/releases)). Cross-compile it on the Mac for `armv7-unknown-linux-musleabihf` with `rustls-tls` and the built-in libmdns, which avoids needing Avahi. Snapclient with the FLAC codec has run on 400 MHz MIPS routers ([snapcast #1013](https://www.github.com/badaix/snapcast/discussions/1013)). Avoid gmrender-resurrect, because it pulls in GStreamer ([Buildroot .mk](https://android-kvm.googlesource.com/buildroot/+/c63dc23b87724635b0d90aad1a52b337f5e95d99/package/gmrender-resurrect/gmrender-resurrect.mk)). None of these daemons has a published RAM measurement on ARMv7. The researchers' estimates are 3–10 MB for shairport-sync-mini and 10–25 MB for librespot (spotifyd measured 13 MB on a desktop, [LinuxLinks](https://www.linuxlinks.com/spotify-qt-lightweight-spotify-client/3/)). Check `VmRSS` during playback.

### Getting sound out: the ES8388 mixer and the QN8027 FM chip

No V831-specific ES8388 mixer recipe was found online. The mainline es8328 driver, which also drives the ES8388, routes playback through "Left/Right Playback Switch" mixer controls and "Output 1/2" volumes ([es8328.c](https://raw.githubusercontent.com/torvalds/linux/master/sound/soc/codecs/es8328.c)). Enabling those playback switches was the fix for "no audio" on a Jetson ([NVIDIA forum](https://forums.developer.nvidia.com/t/the-audio-codec-es8388-does-not-work-on-jetson-nano/229432/43)). Run `amixer -c 2 contents` first, because the vendor 4.9 control names may differ. Search the stock firmware backup for the exact `amixer`/`tinymix` lines.

The **QN8027 is controlled over I2C only (7-bit address 0x2C) and takes analog audio on its ALI/ARI pins**. It has no I2S input, so whichever analog codec output is wired to it (probably ES8388 OUT2, or card 0's line out) is your FM feed. Frequency is `76 + 0.05 × CH` MHz in a 10-bit channel field split across registers 0x00[1:0] and 0x01. Setting register 0x00 bit 5 (TXREQ) starts transmission, and register 0x02's timer bits = 11 stop the chip switching itself off after 60 s of silence ([QN8027 datasheet](https://elektrotanya.com/sites/default/files/comment/2025/05/qn8027_quintic.pdf); [Arduino QN8027 library](https://github.com/dragon-engineer/QN8027)). Your scan found the chip at i2c-3/0x2c. Try `/dev/qn8027` first by recovering its ioctls from the stock app with `strings` or Ghidra. If that fails, drive the registers directly with `i2cset -f -y 3 0x2c …`. Use the crystal setting the stock driver writes (12 vs 24 MHz is unknown), and keep transmit power modest for legal reasons. Retail listings for these screens describe exactly this design: audio to the car "via FM frequency or the included AUX cable" ([desertcart listing](https://desertcart.sg/zh/products/607272293-bigthree-car-stereo-wireless-apple-carplay-android-auto-portable-7)).

| Internet radio / Mac-relayed YouTube audio | mpg123 | **GO** | few MB |

## Touch works best as a single pointer or as big buttons

The GT911 at `/dev/input/event4` already reports coordinates in the 0–1600 × 0–600 range that matches fb0, so no calibration is needed. The limit is macOS, which **does not support touchscreens natively**. Elo says Mac HID "does not support Elo Touch Monitors" without its UPDD driver ([Elo support](https://elosupport.elotouch.com/hc/en-us/articles/31649127329815-MAC-HID-Support-Driver-and-FW-Docs)), and a developer reports macOS only reading a digitizer's single-touch interface ([Apple forums 829408](https://developer.apple.com/forums/thread/829408)). The dependable design is network injection. A roughly 100-line C reader on the device sends touch down/move/up over UDP or TCP. A Mac daemon maps them to the virtual display's global bounds and posts CGEvent mouse and scroll events. One finger acts as click and drag, and two fingers scroll. Pinch and rotate cannot be synthesised through public APIs. OpenDisplay already implements this mapping.

For a **Stream Deck-style macro pad**, Bitfocus Companion's Satellite API is the best target. It is a line-based text protocol on TCP 16622. The client registers a surface with `ADD-DEVICE` (any key count, square or custom-sized bitmaps), receives per-key `KEY-STATE` raw RGB bitmaps, and sends `KEY-PRESS` ([Satellite API](https://companion.free/for-developers/Satellite-API)). Companion on the Mac then runs the actions. The official Satellite client needs Node.js on x64/arm64 ([companion-satellite](https://github.com/bitfocus/companion-satellite)), so a **native C client of a few hundred lines** is required. An 8×3 grid of ~190 px keys fits the 1600x600 screen well. For a self-contained UI such as Home Assistant tiles or local media controls, **LVGL** fits: it needs about 180 kB of flash and tens of kB of RAM ([LVGL requirements](https://lvgl.io/docs/open/introduction/requirements)), and its Linux port ships fbdev and evdev drivers ([lv_port_linux](https://github.com/lvgl/lv_port_linux)). You would replace the flush callback with one that issues the dirty-rect pan, about 40 lines. Slint expects OpenGL ES or KMS, and Qt is too large for flash, so neither suits this screen. The Home Assistant REST and WebSocket APIs with a long-lived token are simple enough to call from C, though it is simpler still to let the Mac proxy them.

USB HID is the one approach the coordinator's facts make tricky. The kernel has no `f_hid` function, but **Linux 4.9's FunctionFS accepts a HID class descriptor and passes the report-descriptor request to user space**, and the kernel documentation's own FunctionFS example is a `hid-daemon` ([f_fs.c v4.9](https://raw.githubusercontent.com/torvalds/linux/v4.9/drivers/usb/gadget/function/f_fs.c); [functionfs.txt](https://raw.githubusercontent.com/torvalds/linux/v4.9/Documentation/usb/functionfs.txt)). A userspace HID keyboard plus "absolute mouse" is therefore possible in principle with no kernel rebuild. It would give media keys and shortcuts with no Mac software at all. No public FunctionFS HID daemon exists to copy ([Toradex thread](https://community.toradex.com/t/composite-hid-device-linux/8278)), the sunxi gadget controller is untested with it, and `otg_role` would have to change from host. Treat it as an experiment for later.

## Roadmap: build the shared pieces first

The order matters because the pieces stack. Each step stays in RAM or uses only a small slice of the free flash, and none changes the kernel, the bootloader or the WiFi setup.

| Step | What to build | Proves / unlocks | Done when |
|---|---|---|---|
| 0 | Benchmarks via command channel: static `tjbench`, `iperf3`, `evtest`; dump `amixer -c 2 contents`; `strings` the stock app for `qn8027`/`amixer` | Replaces the estimates in this report with real numbers | Real fps and Mbit/s figures recorded |
| 1 | OpenWrt-musl prefix with alsa-utils, mpg123, shairport-sync-mini; ES8388 mixer; QN8027 tune | Music + FM; shows foreign musl binaries run here | Mac AirPlays to the screen and the car radio plays it |

## Risks, gaps and unverified numbers

The biggest technical risk is that **macOS can remove the private CGVirtualDisplay API** in any update. Check that it is available at startup and fall back to mirroring a window. ScreenCaptureKit also asks for Screen Recording permission again periodically on recent macOS, so run the daemon as a signed app bundle so the permission persists. On the device, **RAM is the binding constraint**: 91.5 MB available and no swap. Anything hosted in tmpfs costs its full size in RAM, which is why RAM-squashfs FBrowser is marginal while the small daemons are comfortable. Stop fbdash before running anything else that draws to fb0. Leave `otg_role` alone until you have confirmed it does not interfere with FEL recovery. Keep everything you install outside the WiFi and command-channel startup path, so a bad binary can be fixed with a reboot rather than by opening the case.

Several numbers in this report are estimates, not measurements. They are: the JPEG decode time (35–50 ms per full frame), WiFi (20–40 Mbit/s) and NCM throughput, every daemon RAM figure, the FBrowser 75–80 MB peak, and 360p software decode viability. Step 0 of the roadmap exists to replace them. Known unknowns: which ES8388 output feeds the QN8027 versus the 3.5 mm jack; the QN8027 crystal frequency and the `/dev/qn8027` ioctls; whether the vendor display driver accepts dma-buf fds in `DISP_LAYER_SET_CONFIG2`; whether MJPEG decode on the video engine is hardware or the "mjpegplus soft" fallback seen in `sdvcam`; and whether a public Tina V83x SDK mirror exists. On prior work: the only public reverse engineering of a V831 CarPlay product is a write-up rooting a **different** V831 + 16 MB NOR dongle over WiFi ([Louis-E, Medium](https://hn.jakechampion.name/reader/https://medium.com/@louis-e/from-wi-fi-access-to-root-reverse-engineering-a-50-carplay-dongle-a3fbeeeb0be9)). The EEVblog "Hacking Podofo 10.26" thread never appeared in web searches, and no whycan, CSDN or Bilibili posts on these screens turned up. Browsing that forum thread directly and searching whycan's MaixII/V831 section for `sample_vdec` and `sun8iw19` are the most valuable follow-ups, because they are the most likely places to find the decoder SDK.

## Conclusion

The research changes the main question from "what can this little computer run?" to "how little does it need to run?" Treated as a network display with a touch sensor and an FM transmitter, the V831 does almost everything you asked for. Treated as a standalone computer, it hits its 91.5 MB limit almost immediately. The constraint that most shapes the plan is the panel's dirty-rectangle pan, not the CPU. Small, targeted updates are cheap and full-screen repaints are not, so desktop-style streaming suits this screen better than video.

The biggest finding is in your own backup: the stock CarPlay app proves the video engine can decode H.264 at panel resolution and output it through G2D and a separate display layer, with no kernel changes. That turns smooth YouTube and a 30 fps Mac display from impossible into blocked by missing libraries. If anyone ever posts the V831 eyesee-mpp SDK, or you work out how to drive `sdvcam`'s own decoder, the same tile client can switch from JPEG to H.264 and every project above gets smoother.
